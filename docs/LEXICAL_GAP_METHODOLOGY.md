# Lexical-Gap Definition — Methodology

Frozen artifact: `data/lexical_gap.json`, generated by `scripts/lexical_gap_analysis.py`
(deterministic, no randomness). Frozen **before** any ranking system was compared on the
lexical-gap slice.

## Why not the obvious definition

The obvious-sounding definition — "queries where BM25 loses and the semantic/hybrid model
wins" — is explicitly rejected because it is circular: it would define the slice using the
very model comparison the slice is later used to explain. Every candidate definition below is
computed purely from query and document **text**, never from any retrieval model's output.

## Candidate definitions considered

All three measured on the **dev split only** (n=90), stopwords removed, against each query's
primary (grade-3) relevant document:

| Candidate | Formula | dev p25 | dev median | dev p75 |
|---|---|---:|---:|---:|
| `jaccard_body` | Jaccard overlap between query content tokens and the full document body's content tokens | 0.074 | 0.140 | 0.167 |
| `coverage_body` | Fraction of query content tokens that literally appear anywhere in the document body | 0.400 | 0.571 | 0.714 |
| `coverage_title` | Fraction of query content tokens that literally appear in the document **title** | 0.286 | 0.500 | 0.667 |

## Evaluation of the three candidates

- **Independence from model performance:** all three are text-only — none looks at BM25,
  dense, or any ranking output. Equally non-circular.
- **Interpretability:** `coverage_title` is the easiest to explain on a whiteboard ("what
  fraction of the words in this query show up anywhere in the answer's title") and gives the
  clearest intuition for *why* a query would be hard for a pure lexical matcher (BM25 weighs
  title terms heavily via `searchable_text = "{title}. {text}"`).
- **Robustness to document length:** `jaccard_body` and `coverage_body` are both confounded by
  document body length — a longer body has more chances to contain a stray query token by
  coincidence, and a shorter body is punished by Jaccard's union-size denominator even when
  fully on-topic. Every document's title is comparably short (this corpus's titles are 4–9
  words), so `coverage_title` is not confounded by length variation the way the body-based
  metrics are.
- **Robustness to query length:** all three are coverage/overlap ratios (already normalized by
  query-token count for the coverage variants; Jaccard normalizes by the union), so none is
  biased by raw query length.
- **Sample size at the chosen threshold:** using each candidate's own dev-derived p25 as the
  threshold, all three would flag roughly a quarter of dev by construction; the real
  differentiator was interpretability and length-robustness above, not count.
- **Reproducibility:** all three are pure functions of the (frozen) corpus/query text; identical
  every run.

## Decision

**`coverage_title` is the frozen primary lexical-gap definition.**

- **Threshold:** `coverage_title < 0.2857` (the dev-split p25 of `coverage_title`, taken as-is
  and rounded to 4 significant figures — not hand-picked to produce a "nicer" count).
- A query is in the **lexical-gap slice** if fewer than 28.6% of its content words appear
  literally in its primary relevant document's title.

## Representative examples (test split)

Pulled directly from `data/lexical_gap.json`'s `per_query_diagnostics`:

- `"connected to vpn but can't reach shared drives"` → target document titled *"VPN connects
  but internal file shares are unreachable"* — shares "vpn"/"connect" but "shared drives" vs.
  "internal file shares" is a genuine paraphrase.
- `"scan to network folder crashes the scanner software"` → target *"Scanner software crashes
  when scanning to a shared network folder directly"* — high body overlap but lower title-token
  coverage once stopwords are stripped, illustrating why `coverage_title` and `coverage_body`
  can disagree on a borderline case.

all three candidate metrics, is in `data/lexical_gap.json` — not reproduced in full here to keep
this document short.)

## Limitations (disclosed, not hidden)

- **The val (n=3) and test (n=5) lexical-gap slices are very small.** Any metric computed on 3
  or 5 queries has enormous sampling variance — a single query flipping from a hit to a miss
  moves the slice's MRR/nDCG by 20–33 percentage points. `docs/BENCHMARK_REPORT.md` reports
  these numbers with that caveat attached every time, and treats them as directionally
  suggestive, not as a precise measurement.
- **The corpus was authored, not sampled from real user paraphrase behavior.** The
  paraphrase/close-vocabulary mixture in `scripts/generate_corpus.py` was deliberate but the
  author did not tag which queries were intended as paraphrases — `coverage_title` was computed
  blind to that intent and is what actually determines slice membership, which is the right
  process, but it does not make the slice a "real" user-behavior lexical-gap sample the way a
  production query log would.
- **`coverage_title` is one reasonable choice among the three candidates, not a provably optimal
  one.** A larger/production corpus might favor `coverage_body` for a longer-document domain
  where titles are less informative. This choice is scoped to this corpus's characteristics
  (uniformly short, descriptive titles).
